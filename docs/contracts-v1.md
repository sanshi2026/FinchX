# FinchX Core Contracts v1

## Status and record classification

DataStatus describes the record's acquisition outcome, timeliness, or whether its value is estimated:

- live: current inputs were obtained for this record; the record may be standardized or freshly derived.
- delayed: the source/input has a known publication or delivery delay.
- reused: a previously captured value is served again rather than newly obtained.
- missing: acquisition succeeded and confirmed the requested record/value is absent.
- failed: acquisition or validation could not establish a usable value.
- estimated: the payload value is an estimate rather than an observed value.

RecordClass is separate: raw is provider payload before normalization, standardized is mapped into FinchX's contract, and derived is calculated from upstream input. These dimensions are independent. For example, a provider-published estimate can be standardized + estimated; a fresh calculation can be derived + live; a cached calculation can be derived + reused; and a FinchX estimate can be derived + estimated. The model does not require estimated records to be derived. Status says whether the value is estimated; recordClass says which processing layer the record belongs to.

Quality is separate from both. QualityIssueKind.estimated is an optional note about an estimate's assumptions or uncertainty; it does not replace status=estimated. When the whole payload is an estimate, use status=estimated whether the estimate came from a provider or FinchX.

## Quality and status rules

- delayed describes a known source/feed lag; stale means a dataset's freshness rule or requested asOf says the value is too old. A delayed value can be fresh for its delayed feed, and a live response can still contain stale content.
- partial means a record exists but some requested fields or components are absent. missing means the requested record/value itself is absent after a successful lookup. Do not use partial to turn a complete miss into a record.
- failed means no usable result could be established due to retrieval or validation failure. It is distinct from missing. A stale quality issue can accompany a reused result; do not mark a retrieval failure as missing.
- Quality issues add observations such as warning, validation concern, stale, partial, or estimate uncertainty. They do not change the acquisition outcome represented by status.

## Source, provenance, and identifiers

Source.providerId identifies the immediate producer of this envelope; sourceRecordId and sourceUrl are optional upstream identifiers. It contains no HTTP settings, retries, rate limits, or other request configuration.

Provenance.sourceReferences identify inputs actually used by a transformation. Do not repeat the same direct provider record in sourceReferences when Source already identifies that record. For derived output, Source identifies the immediate FinchX transformation (for example finchx.derived), while sourceReferences identify its upstream provider records. transformationVersion and adjustments describe the processing without creating a lineage engine.

recordId is owned and ultimately generated by FinchX, distinct from provider sourceRecordId. It must remain stable for the same semantic record. This Stage requires recordId explicitly but defers the generation policy; no algorithm is part of this contract review.

InstrumentId is an explicit code + market + kind, with optional exchange. Market identifies the A-share universe; Exchange identifies SSE, SZSE, or BSE as venue; InstrumentKind distinguishes equity, index, and ETF. This Stage performs no code parsing, normalization, or market inference. A string entityId is an opaque key for non-instrument entities, never an instruction to parse a stock symbol.

## Time and timezone

eventAt is when the described event happened. publishedAt is when a source first published the information. updatedAt is when that source later changed it. capturedAt is when FinchX captured the record and is required. asOf is the query or knowledge cutoff. Source publication/update times are never replaced by capturedAt.

Python accepts aware datetime objects or RFC 3339 timestamp strings with an explicit whole-minute offset. Naive values, Unix timestamps, and looser date-time spellings are rejected. Strings use a T separator, seconds, up to six fractional-second digits (Python datetime precision), and Z/z or a numeric offset; lowercase z is serialized as canonical uppercase Z. -00:00 is rejected because it means the local offset is unknown. JSON Schema includes both date-time format and an offset-bearing pattern. Format-aware validators should assert date-time format.

A-share exchange-local time is represented with Asia/Shanghai's UTC+08:00 offset; UTC uses Z or +00:00. The instant 2026-09-17T09:30:00+08:00 is semantically equal to 2026-09-17T01:30:00Z. Python compares them as the same instant. Serialization preserves the supplied offset and does not rewrite all values to UTC. JSON carries the offset, not an IANA zone name. These fields describe instants, not trading-date labels.

## Units and numeric representation

The first A-share contracts use CNY for prices and monetary amounts. Python contracts use Decimal for price, amount, and ratio values and integers for shares. Callers provide Decimal values or canonical decimal strings; binary floats, integers, non-finite values, and non-canonical decimal strings are rejected for Decimal unit types.

The public JSON choice is deliberate and independent of Python's Decimal type: price, amount, percentage, and dimensionless ratio values serialize as canonical decimal strings, while share counts remain JSON integers. This preserves exact digits across JavaScript and other SDKs and avoids silently routing large monetary values through binary floating-point. The tradeoff is that JSON consumers must parse decimal strings for arithmetic; JavaScript users need a decimal library or an explicit precision-losing Number conversion. Python users can use Decimal directly. Pandas/NumPy users must explicitly convert at the analysis boundary, which can cost vectorization if values remain object/string columns. Future Arrow/Parquet storage can use typed decimal columns independently of the JSON wire format.

Percentages use ratio fractions consistently: 4.24% is Decimal("0.0424"), serialized as "0.0424", never 4.24. A generic dimensionless Ratio is expressed in times (2.35 means 2.35x) and remains distinct from Percentage. units.schema.json is the JSON contract for these exact decimal strings. Each dataset schema must identify the currency and unit of every field; the generic envelope payload remains open until a dataset has its own schema.

## Schema version and source of truth

schemaVersion is the string "1.0" for this first envelope contract. Dataset names are lowercase stable names such as instrument, trading_calendar, market.quote, and market.klines.

The versioned JSON Schemas in the packaged `finchx.schemas/v1/` resources are the normative wire contract and are authored before model changes. Use `finchx.schemas` to load them; do not resolve repository-root paths. Offline tests validate synthetic examples and Python serialization against those schemas, compare fields/required fields/enums, and check decimal and timestamp behavior. Dataset payload fields remain open until each dataset gets its own schema.

## Runtime model dependency

Pydantic v2 is the one runtime model dependency. Its nested validation, enums, JSON aliases, datetime checks, and serialization keep the Python boundary small and testable. Dataclasses would need hand-written validation, alias mapping, nested parsing, datetime serialization, and round-trip logic, duplicating the schema contract.

## Schema distribution

Recommendation: schemas are a FinchX public package resource and should ship in the wheel so installed users and other SDKs can validate the public data contract. The canonical files live once under `src/finchx/schemas/v1/` and are included in the wheel as `finchx.schemas/v1/`; there is no unchecked duplicate schema copy. The resource loader and clean-wheel installation are covered by regression tests.
